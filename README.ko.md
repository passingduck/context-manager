# context-manager

[English](README.md)

`context-manager`는 실행 파일 하나입니다. Claude Code, Codex CLI, Gemini CLI가 프로젝트 디렉터리에서 모델에게 실제로 보내는 내용을 보여 줍니다. 어떤 지침 파일이 어떤 순서로 불러와지는지, 토큰을 얼마나 차지하는지, 어디가 잘리는지를 보여 줍니다. 그 파일과 훅과 메모리를 직접 고칠 수도 있으며, 모든 쓰기 전에 미리 보기가 나오고 변경 기록을 되돌릴 수 있습니다.

## 빌드와 설치

Rust(stable, edition 2024)와 Node.js와 pnpm이 필요합니다. 설치 스크립트는 UI를 빌드하고 릴리스 바이너리를 빌드한 뒤 `~/.local/bin`에 복사합니다. `PREFIX`에 디렉터리를 지정하면 그곳에 복사합니다. 스크립트는 `sudo`를 쓰지 않습니다.

```sh
scripts/install.sh               # 데스크톱 빌드: 창과 --serve를 모두 지원합니다
scripts/install.sh --headless    # 창이 없는 빌드: --serve만 동작합니다 (약 13.5 MB)
PREFIX=$HOME/bin scripts/install.sh --headless
```

창이 없는 빌드에는 GUI 라이브러리가 필요하지 않으므로 Linux 서버에는 이 빌드를 설치합니다. Linux용 빌드에 clippy 경고가 없는지 확인하려면 `scripts/check-linux.sh`를 실행합니다. 프로젝트의 모든 검사를 돌리려면 `scripts/check.sh`를 실행합니다. 이 스크립트는 Linux 대상이 설치되어 있으면 Linux 검사도 함께 실행합니다. 릴리스 빌드를 임시 홈에서 실행하고 헤드리스 Chrome으로 실제 화면을 조작해 확인하려면 `scripts/e2e.sh`를 실행합니다. 이 스크립트는 Node 24와 Chrome 또는 Chromium이 필요하며 `check.sh`에는 포함되지 않습니다.

## 실행

```sh
context-manager                       # 현재 디렉터리를 창으로 엽니다
context-manager --path ~/work/app     # 다른 프로젝트 디렉터리를 엽니다
context-manager --serve               # 같은 UI를 127.0.0.1:7457에서 HTTP로 제공합니다
context-manager --serve --port 0      # 비어 있는 포트를 골라 씁니다
context-manager --serve --host 0.0.0.0 --port 8080
context-manager --read-only           # 모든 쓰기와 훅 실행을 거부합니다
```

`--serve`는 토큰이 붙은 주소를 출력합니다.

```
http://127.0.0.1:7457/#token=3f9c...
```

이 주소를 브라우저에서 엽니다. 토큰은 주소의 조각(fragment) 부분에 들어 있으므로 브라우저가 서버로 보내지 않습니다. 페이지는 토큰을 세션 동안 보관하고 주소창에서 지웁니다. 모든 API 요청에는 이 토큰이 필요합니다. 시작할 때마다 같은 토큰을 쓰려면 `CONTEXT_MANAGER_TOKEN`을 지정합니다.

```sh
CONTEXT_MANAGER_TOKEN=choose-a-long-secret context-manager --serve
```

서버는 암호화되지 않은 HTTP를 사용하고, 토큰을 가진 클라이언트는 그 컴퓨터에서 훅을 실행할 수 있습니다. 기본값인 루프백 주소에 바인딩하고, 원격 서버에는 SSH 터널로 접속합니다.

```sh
ssh -L 7457:127.0.0.1:7457 user@server       # 내 노트북에서 실행합니다
context-manager --serve --path ~/work/app    # 서버에서 실행합니다
```

그다음 노트북의 브라우저에서 출력된 주소를 엽니다. `--host`에 루프백이 아닌 주소를 주면 경고가 출력됩니다. 그 주소에 접근할 수 있고 토큰을 가진 사람은 누구나 그 컴퓨터에서 명령을 실행할 수 있기 때문입니다.

## 보여 주는 것과 고칠 수 있는 것

프로젝트와 홈 디렉터리에서 찾은 각 에이전트에 대해 다음을 보여 줍니다.

- **컨텍스트.** 모든 지침 파일, 규칙, 가져오기(import)를 불러오는 시점별로 묶어 보여 줍니다. 시점은 세션 시작, 에이전트가 파일을 열 때, 사용자가 호출할 때, 에이전트가 읽기로 선택할 때입니다. 세션 시작 때 모델에게 전달되는 텍스트를 글자 그대로 보여 주고, 그 합계로 토큰 예산을 계산합니다. 각 파일이 그 텍스트의 어디에 놓이는지는 막대로 보여 줍니다. 건너뛰었거나 가려졌거나 잘린 파일은 그 이유와 함께 보여 줍니다. 한 파일이 여러 곳에서 불러와지는 경우도 있습니다. 예를 들어 지침 파일이 스킬 파일을 가져오면, 그 스킬은 가져온 본문과 스킬 목록의 한 줄로 두 번 들어갑니다. 이때 도구는 곳마다 모델이 받는 텍스트를 따로 보여 줍니다.
- **메모리.** 메모리 저장소와 그 항목을 보여 줍니다.
- **훅.** 모든 훅의 이벤트, 매처, 핸들러, 상태를 보여 주고, 켜고 끄는 스위치와 새 훅 양식과 시험 실행을 제공합니다.
- **확장.** 스킬, 명령, 서브에이전트를 보여 줍니다.
- **진단.** 존재하지 않는 훅 프로그램, 해석되지 않는 설정 파일, 존재하지 않는 파일로 가는 링크 같은 문제를 보여 줍니다. 가져오기 때문에 본문이 세션마다 들어가는 스킬도 보여 줍니다.
- **기록.** 도구가 만든 모든 변경을 차이(diff)와 되돌리기와 함께 보여 줍니다.
- **검색과 경로 시뮬레이터.** 에이전트가 불러오는 내용을 검색하고, 에이전트가 이 경로를 열면 어떤 파일이 불러와지는지 보여 줍니다.

에이전트가 읽는 파일은 무엇이든 추가하고 고치고 지울 수 있습니다. 에이전트나 플러그인이 직접 관리하는 파일은 예외이며, 이런 파일은 이유와 함께 읽기 전용으로 열립니다.

## 쓰기를 보호하는 방법

1. **미리 보기.** 모든 편집은 먼저 계획을 세웁니다. 아무것도 쓰기 전에 정확한 차이와 모든 경고를 볼 수 있습니다. 쓰기는 계획이 미리 본 것과 같을 때만 적용됩니다.
2. **충돌.** 파일을 연 뒤에 디스크의 파일이 바뀌었다면 저장은 충돌이 되고 현재 텍스트를 보여 줍니다. 도구가 파일을 덮어쓰는 일은 없습니다.
3. **휴지통.** 삭제한 파일은 운영체제의 휴지통으로 갑니다. 데스크톱이 없는 Linux 서버에는 휴지통이 없습니다. 그런 곳에서 도구는 변경 기록이 내용을 완전히 보관하는 파일과 디렉터리만 지웁니다. 그리고 결과에 휴지통으로 보내지 않았다고 표시합니다. 이진 파일이 들어 있는 디렉터리처럼 변경 기록이 완전히 보관하지 못하는 디렉터리는 지우지 않고, 작업은 실패합니다. 프로그램을 시작하기 전에 `CONTEXT_MANAGER_NO_OS_TRASH`를 설정하면 프로그램은 운영체제의 휴지통을 쓸 수 없는 것으로 다룹니다. 이 설정은 되돌리기로 복원할 수 없는 것을 지우지 않습니다.
4. **기록.** 변경을 적용하기 전에 도구가 이전 내용을 저장합니다. 적용이 실패하면 도구는 쓴 것을 되돌리고 그 변경을 취소됨으로 기록합니다. 프로그램이 죽어서 중단된 변경은 도구가 나중에 혼자 마무리하지 않습니다. 도구는 시작할 때 파일을 읽기만 합니다. 모든 파일이 새 내용이면 그 변경을 완료로 기록합니다. 모든 파일이 이전 내용이면 취소됨으로 기록합니다. 두 경우가 섞여 있으면 끝나지 않은 변경으로 화면에 표시합니다. 그러면 사용자가 그 변경을 되돌리거나 편집을 다시 적용합니다.
5. **되돌리기.** 기록의 항목은 자체 미리 보기가 있는 새 변경으로 되돌립니다. 삭제한 파일은 기록에 저장된 사본에서 복원하므로 휴지통을 비워도 되돌릴 수 있습니다.

도구는 이 경로로만 파일을 쓰며, 사용자 대신 승인을 기록하지 않습니다. 신뢰 해시, 신뢰 파일, 확인 파일을 쓰지 않습니다.

다음 세 경우는 다르게 동작합니다.

- 없는 파일을 가리키는 심볼릭 링크에는 도구가 쓰지 않습니다.
- 하드 링크가 둘 이상인 파일은 제자리에 덮어씁니다. 그래야 모든 이름에서 변경이 보입니다. 이 쓰기는 원자적이지 않으며, 미리 보기가 그 사실을 경고합니다.
- 도구 두 개가 같은 데이터 디렉터리를 함께 쓸 수 있습니다. 한쪽이 아직 쓰고 있는 변경을 다른 쪽이 닫지 못하도록 잠금 파일이 막습니다.

## 훅을 끄면 일어나는 일

| 에이전트 | 도구가 쓰는 내용 |
|---|---|
| Codex CLI | 사용자 `config.toml`의 `[hooks.state."<key>"]` 아래에 `enabled = false`를 씁니다. 다시 켜면 그 키를 지웁니다. |
| Gemini CLI | `settings.json`의 `hooksConfig.disabled`에 훅의 이름을 씁니다. 이름이 없으면 명령을 씁니다. 항목 하나가 여러 훅을 끌 수 있으며, 미리 보기에 그 개수가 나옵니다. |
| Claude Code | Claude Code에는 끄는 기능이 없습니다. 도구가 설정 파일에서 핸들러를 지우고 자신의 데이터 디렉터리에 저장합니다. 그 훅은 꺼진 상태로 목록에 남고, 다시 켜면 원래 자리에 돌아옵니다. |

플러그인이나 관리형 설정에서 온 훅은 업데이트 때 덮어써지므로 끌 수 없습니다.

## 도구가 데이터를 저장하는 곳

플랫폼의 데이터 디렉터리에 저장합니다. macOS에서는 `~/Library/Application Support/context-manager`이고, Linux에서는 `$XDG_DATA_HOME/context-manager`(보통 `~/.local/share/context-manager`)입니다. 다른 디렉터리를 쓰려면 `CONTEXT_MANAGER_DATA_DIR`을 지정합니다. 이 디렉터리에는 `history/changes`(변경마다 JSON 파일 하나), `history/blobs`(저장된 파일 내용), `parked/`(꺼 둔 Claude Code 훅)가 들어 있습니다. 이 디렉터리는 현재 사용자만 접근할 수 있습니다. 도구는 이 밖의 데이터를 저장하지 않으며, 스캔은 파일 시스템과 환경 변수만 읽습니다.

## 무엇을 검증했고 무엇을 검증하지 못했는가

- **Codex CLI.** 설치된 CLI와 대조했습니다. 세션 시작 텍스트는 `codex debug prompt-input`의 출력과 바이트 단위로 일치하고, 훅 목록과 훅 해시는 `hooks/list`의 응답과 일치합니다.
- **Claude Code.** 설치된 실행 파일을 로컬 싱크에 대해 열 가지 시나리오로 실행해 대조했습니다. 설정을 바꾸는 계획을 적용할 때마다 `claude doctor`가 그 파일을 통과시킵니다.
- **Gemini CLI.** 한 번도 실행하지 않았습니다. 규칙은 v0.69.0 태그의 소스에서 가져왔고, 어댑터의 테스트는 픽스처로만 그 규칙을 확인합니다.
- **쓰기 흐름.** 헤드리스 Chrome에서 실제 UI로 시험했고, 임시로 만든 홈 디렉터리에서만 실행했습니다. 실제 에이전트 홈에서는 실행하지 않았습니다.
- **쓰기 절차.** 테스트와 별도로 `TLA+` 모델을 TLC로 검사했습니다. 모델은 적용, 실패했을 때의 되돌림, 복구, 되돌리기, 잠금을 담고 있습니다. TLC는 도구 두 개의 단계가 섞이는 모든 순서를 검사합니다. 프로그램이 한 번 죽는 경우, 파일 작업이 한 번 실패하는 경우, 바깥에서 파일을 두 번 고치는 경우가 범위에 들어 있습니다. `formal/write-pipeline/run.sh`가 이 검사를 몇 분 안에 실행합니다. 통과는 이 범위에 대해서만 성립합니다. 모델이 찾은 결함 두 건은 아직 고치지 않았으며, 아래 한계의 처음 두 항목입니다.
- **토큰 수.** o200k 토크나이저로 구한 추정값입니다. Claude와 Gemini는 다른 토크나이저를 쓰므로 실제 값은 다릅니다.
- **Linux.** 창이 없는 빌드는 `scripts/check-linux.sh`로 컴파일만 확인했습니다. Linux에서 실행한 적은 없으며, 데스크톱이 없는 Linux 서버에서 휴지통이 어떻게 동작하는지도 시험하지 못했습니다.

## 한계

- **제자리 쓰기의 실패.** 하드 링크가 둘 이상인 파일을 쓰다가 중간에 실패하면 파일이 반쯤 쓰인 채 남습니다. 디스크가 가득 찼을 때 이런 일이 생길 수 있습니다. 이때 기록은 그 변경을 취소됨으로 표시합니다. 이전 내용은 기록에 남아 있지만, 도구는 그 내용으로 되돌리는 방법을 제공하지 않습니다.
- **쓰는 순간의 틈.** 도구는 파일의 해시를 확인한 다음 새 파일의 이름을 그 파일의 이름으로 바꿉니다. 두 단계 사이에 다른 프로그램이 파일을 고치면 그 내용은 덮어써지고 기록에도 남지 않습니다. 이 틈은 시스템 호출 한 번 정도의 길이입니다.
- **훅의 시험 실행.** 시험 실행이 제한 시간을 넘기면 도구는 훅의 프로세스 그룹을 종료합니다. 훅이 `setsid`로 새 세션에서 프로세스를 시작하면 그 프로세스는 계속 실행될 수 있습니다.
- **새 Claude Code 메모리.** 도구가 만든 메모리에는 항상 `metadata.type: project`가 들어갑니다.
- **크거나 악의적인 저장소.** 스캔은 파일 하나에서 최대 8 MiB를 읽고, 전체로는 최대 64 MiB를 읽습니다. 디렉터리 트리 하나에서는 항목 2,000개와 깊이 8단계까지만 나열하고, 프로젝트에서는 항목 20,000개까지만 훑습니다. 가져오기를 펼치는 양은 파일 하나에 4 MiB, 스캔 한 번에 8 MiB까지입니다. 상한에 닿아도 스캔은 계속됩니다. 어느 상한에 닿았는지는 진단 화면이 보여 줍니다.
